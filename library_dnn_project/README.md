# 📚 Deep Neural Network Based Library Book Demand Prediction & Intelligent Recommendation System

A full-stack, **software-only** college project. A DNN (Keras/TensorFlow) learns from
historical library borrowing data to forecast **future book demand** (next
week / semester / exam season) and powers an **intelligent recommendation
engine** that combines a student's reading interest, current book
availability, and predicted future demand.

No special hardware needed. No real dataset needed — a realistic **synthetic**
library dataset (books, students, 2 years of borrow transactions with
semester/exam/vacation seasonality) is generated by the project itself.

## 3. Where and Why the DNN Is Used

**Task:** predict how many times a book will be borrowed **next week**,
per book, from features like:

| Feature | What it captures |
|---|---|
| `lag_1..lag_4` | last 4 weeks' borrow counts (recent trend) |
| `rolling_avg_4` | smoothed recent demand |
| `is_exam_period`, `is_vacation` | calendar/season signal |
| `month_sin/cos`, `week_sin/cos` | cyclical time-of-year encoding |
| `category_encoded`, `department_encoded` | subject-area signal |
| `total_copies`, `base_popularity` | catalog/supply + long-run popularity |
| `dept_week_demand` | department-wide pressure that week (e.g. all CS books spike before a CS exam) |

**Why a DNN and not a simple formula / linear regression?**
Demand is driven by **non-linear interactions** between these features —
e.g. `is_exam_period × category` matters a lot (a "Data Structures" book
spikes hard before a CS exam, a "Fiction" book barely moves), and
`department_encoded × dept_week_demand` compounds that further. A single
linear formula can't represent these interactions well; a small feed-forward
DNN (`64 → 32 → 16 → 1` Dense layers with BatchNorm + Dropout, trained with
Adam + early stopping) learns them directly from data. The dataset (≈80k+
book-week rows) is large enough to train this network without overfitting,
which is exactly the situation where a compact DNN outperforms both plain
heuristics and adds interpretability advantages over a black-box like
gradient boosting for a viva explanation.

The trained network is reused (not retrained) for:
- weekly demand prediction
- the 0–100 demand score
- what-if simulation (same model, calendar flags flipped)

This is explicitly called out in `model/train_model.py`'s docstring — read
it before your viva, it's written as an answer to "why DNN here?".

|---|---|---|---|

| 16 | 📦 Smart Acquisition Planner | `advanced_features.smart_acquisition_planner()`, "Smart Planning" tab | Recommends exact extra-copy counts over a horizon (default 1 month), using syllabus/calendar-adjusted demand and each book's real `unit_cost`. |
| 17 | ♻️ Overstock Detection | `advanced_features.overstock_detection()`, Alerts tab | The mirror image of #16 — flags books with far more copies than adjusted demand justifies, and estimates money that could be saved. |

| 20 | 🔮 What-If Simulator (extended) | `advanced_features.what_if_new_course()`, `what_if_enrollment_change()`, "What-If Simulator" tab | On top of the existing exam/vacation/normal simulator: simulate launching a new course, or a department-wide enrollment change, and see demand move — using the same trained predictor. |
| 21 | 🏫 Department-wise Forecasting | `advanced_features.department_semester_forecast()`, Analytics tab | Adjusted demand aggregated per department, alongside each department's active semester type and the next calendar event. |
| 22 | 🚨 Proactive Alerts | `advanced_features.proactive_alerts()`, Overview tab | Unified feed combining low-stock alerts + upcoming shortages + anomaly spikes + overstock — one place for a librarian to check every morning. |

**Still-earlier bonus features (kept from the first version):**
- Low-usage / "dead stock" detector (`/api/low-usage-books`) — a simpler precursor to Overstock Detection
- Cold-start handling in the recommender
- Graceful DNN → statistical fallback (the whole system, including every new feature above, keeps working even before `train_model.py` has been run — every new module calls into the same `PREDICTOR.predict_batch()`, so it inherits the fallback automatically)

## 4B. How the New Features Combine With the DNN (architecture note)

```
                     ┌───────────────────────────┐
 historical borrows  │   DNN (train_model.py)     │   raw predicted_demand,
 ──────────────────► │   Dense 64→32→16→1         │ ─► demand_score (0-100)
                      └───────────────────────────┘        (UNCHANGED)
                                    │
                                    ▼
                 ┌──────────────────────────────────────┐
 subjects +      │  Context Adjustment Layer              │   adjusted_predicted_demand,
 academic_calendar├─► (academic_context.py +               ├─► adjusted_demand_score,
                 │   advanced_features.get_enhanced_       │   boost_reason,
                 │   predictions())                        │   prediction_confidence
                 └──────────────────────────────────────┘
                                    │
              ┌─────────────────────┼─────────────────────────┐
              ▼                     ▼                          ▼
   Shortage / Acquisition /   Explainable AI            Proactive Alerts /
   Overstock / Budget         (explain_demand)           Department Forecast
```

The DNN is trained exactly once and never retrained by any of the new
features — they all consume its output (or the fallback's output, via the
same `PREDICTOR.predict_batch()` interface) and add a transparent rules
layer on top. This keeps the core "why DNN" story from Section 3 completely
intact while making the system's numbers syllabus- and calendar-aware.

## 5. Recommendation Engine — the Core Novelty

```
final_score = 0.45 × interest_score        (from student's own borrowing history)
            + 0.20 × availability_score    (is a copy on the shelf right now)
            + 0.35 × demand_score          (DNN-predicted future demand)
```

This is intentionally simple and **explainable** — you can defend every term
in a viva — while still being genuinely "AI-based" because the demand_score
component comes straight from the trained DNN, and it's the piece that makes
recommendations forward-looking instead of just "more of what you already
read."

## 8. Retraining / Extending

- Re-run `python data/generate_data.py` any time to regenerate a fresh
  synthetic dataset (edit `NUM_BOOKS`, `NUM_STUDENTS`, `START_DATE`/`END_DATE`
  at the top of the file to scale it up or down).
- Re-run `python model/train_model.py` after any data change — it rebuilds
  the training table from `feature_engineering.py` and retrains from scratch.
- All thresholds (alert sensitivity, inventory-suggestion aggressiveness,
  recommendation score weights) are plain constants/arguments in
  `model/predict.py` — easy to tune and explain in a viva.

## 9. Suggested Viva / Demo Flow

1. Show `data/generate_data.py` → explain the synthetic seasonality logic.
2. Show `model/train_model.py` → explain the DNN architecture and *why* DNN.
3. Run training live (or show `metrics.json` + `training_history.png` if
   already trained) → MAE/RMSE/R² on held-out test data.
4. Open the dashboard:
   - **Overview** → summary cards + past-vs-forecast trend chart
   - **Demand Predictions** → per-book DNN output + demand score
   - **Alerts & Inventory** → high-demand/low-availability + extra-copy suggestions
   - **Recommendations** → type a student ID, show reading pattern + the
     3-way blended recommendation score
   - **Alternatives** → type a book ID, show similar in-stock alternatives
   - **Analytics** → category/department bar charts
   - **What-If** → switch scenario to "Exam Season" live and show demand
     scores jump — this is the strongest live demo moment since it proves
     the model learned seasonality, not just memorized averages.
